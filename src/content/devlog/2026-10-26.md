Went through my own review notes today. Six items, one commit each. Cleaning a desk I'd been ignoring for weeks, and it felt great.

The initial commit went in first, after a pre-commit review pass. Haiku as the coordinator, fresh Opus workers per task, state in SQLite. The review's first finding scared me. If a transcript went missing, resume would brick the session forever. Cleanup deletes after thirty days by default, so this wasn't theoretical. Joder. Fixed the fallback.

The same review found the real smell. The "don't re-dispatch" rule lived in the model's good manners, and the coordinator was obeying it. Delegation and decision recording are now gated in code and pulled from the allowed tools. Now it can't disobey. That feels better than hoping.

The system prompt is static now, with one briefing per reopen. That fixed prompt caching and a run log that grew without bound. Cheaper than I expected.

Decisions got IDs and a supersedes field. The migration for old data only counts if it runs against real v1 data, not fresh data, so I ran it against a copy of the real thing. Not glamorous. Necessary. Status reads a mirror file, because the storage has no cross-process locking. You only learn that by writing the second process.

The /new escape hatch exists because one CLI error repeats on every retry, and the SDK only says "invalid request". I refused to string-match error messages. Ask me again in a month.

Worker turn limit went from 30 to 100. When it hits, the session resumes for one report-only turn with every permission denied. Honestly, a neat bit of plumbing.

Output escaping now covers control and bidi characters. The gotcha: JSON.stringify misses U+202E, and my tooling had decoded the \u escapes into literal bidi characters in the source. I had to build them from char codes. Seven tests green. Nothing live-tested.

Late in the day, the plan-limit work. A rejected rate-limit status pauses the run, and chat refuses sends until the reset time. A rate-limit event can also abort in-flight requests, but those can still get billed, because the report arrives with a response. So the real guard is turning off extra usage on the account. The code is a seatbelt, not a brake. The limit logic passes 8 of 8 on synthetic events, which is a very clean number for something I've never actually seen happen.

Good day, the kind where I decided things and didn't write a spreadsheet about them. The background hum is still there, the one asking whether anyone will run this besides me. Probably not yet. Doesn't matter tonight.
