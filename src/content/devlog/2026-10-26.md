First commit of the durable coordinator. Haiku coordinates, fresh Opus workers do the coding through the Agent SDK, and state lives in SQLite. Then I reread my own pre-commit review and it was not a clean commit.

The worst one: if a transcript went missing, resume would brick the session forever. Cleanup deletes after thirty days by default, so this wasn't theoretical. Joder. Fixed the fallback.

I also moved the "don't re-dispatch" rule out of the model's good manners and into code. The coordinator was obeying the instruction. Now it can't disobey. That feels better than hoping. While I was in there, I split the prompt into a static system prompt plus one briefing per reopen. That fixes prompt caching and stops the run records from growing without bound.

Then the sweep. Six items, one commit each. Cleaning a desk I'd been ignoring for weeks, and it felt great.

Decisions got IDs and a supersedes field. The migration for old data only counts if it runs against real v1 data, not fresh data, so I ran it against a copy of the real thing. Not glamorous. Necessary.

Status now reads a mirror file instead of the database, because the storage layer is one process with no cross-process locking. Boring plumbing, and the kind that bites you later if you skip it.

The /new escape hatch exists because one CLI error repeats on every retry, and the SDK only says "invalid request". I refused to string-match error messages. Ask me again in a month.

Worker turn limit went from 30 to 100. When it hits, the session resumes for one report-only turn with every permission denied. Honestly, a neat bit of plumbing.

Write previews show the first thirty lines, and anything that could hide text gets escaped. Gotcha of the day: JSON.stringify doesn't escape the right-to-left override character, and the tool pipeline had turned my \u escapes into the literal characters in the source. I had to build them from char codes. Seven tests green. Nothing live-tested.

Late in the day, the plan-limit work. The SDK sends a rate-limit event. When the status is rejected and extra usage is on, the CLI aborts in-flight requests with a plan-limit reason, and the sibling streams record the plan limit instead of a generic abort. The run goes to paused, and chat refuses sends until the reset time. Good so far.

But an abort doesn't stop billing. In-flight requests can still get charged, because the report arrives with a response. So the real guard is turning off extra usage on the account. The code is a seatbelt, not a brake.

Untested against a real limit. The logic passes 8 of 8 on synthetic events, which is a very clean number for something I've never actually seen happen.

Good day, the kind where I decided things and didn't write a spreadsheet about them. The background hum is still there, the one asking whether anyone will run this besides me. Probably not yet. Doesn't matter tonight.
