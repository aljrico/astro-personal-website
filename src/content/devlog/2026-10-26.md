Committed the durable coordinator first: a cheap Haiku coordinator, fresh Opus workers through the Agent SDK, state in SQLite. Then I went through my own review notes. Six items, one commit each. Cleaning a desk I'd been ignoring for weeks, and it felt great.

Before the commit, two things needed fixing. The first one scared me. If a transcript went missing, resume would brick the session forever. Cleanup deletes after thirty days by default, so this wasn't theoretical. Joder. Fixed the fallback.

The second one was about trust. The "don't re-dispatch" rule lived in the model's good manners. The coordinator was obeying the instruction. Now the permission check gates the delegate and decision tools in code, and they're off the allowed list. That feels better than hoping.

I also stopped rebuilding the system prompt on every reopen. It's static now, and each fresh session gets one briefing about project state. Prompt caching works again, and the run records store what I typed, not the briefing.

Then the sweep. Decisions got IDs and a supersedes field. The migration for old data only counts if it runs against real v1 data, not fresh data, so I ran it against a copy of the real thing. Not glamorous. Necessary.

The store is one process with no cross-process locking, so status reads a state.json mirror while the coordinator holds the lock. Smoke runs got a flag instead of the old save switch.

The /new escape hatch exists because one CLI error repeats on every retry, and the SDK only says "invalid request". I refused to string-match error messages. Ask me again in a month.

Worker turn limit went from 30 to 100. When it hits, the session resumes for one report-only turn with every permission denied. Honestly, a neat bit of plumbing.

The Write prompt now shows the first 30 lines, and Bash output is never clipped. printable() escapes control and bidi characters. JSON.stringify misses U+202E, and the tool pipeline turned my \u escapes into literal bidi characters in the source. Of course it did. I fixed it by building them from char codes. Seven tests green. Nothing live-tested.

Late in the day, the plan-limit work. The SDK sends a rate-limit event. When the status is rejected and extra usage is on, the CLI aborts the shared controller with a plan-limit reason, so sibling streams record a plan limit instead of an AbortError. The run goes to paused, and chat refuses sends until the reset time.

A rate-limit event can abort in-flight requests, but those can still get billed, because the report arrives with a response. So the real guard is turning off extra usage on the account. The code is a seatbelt, not a brake.

The limit logic passes 8 of 8 on synthetic events, which is a very clean number for something I've never actually seen happen.

Good day, the kind where I decided things and didn't write a spreadsheet about them. The background hum is still there, the one asking whether anyone will run this besides me. Probably not yet. Doesn't matter tonight.
